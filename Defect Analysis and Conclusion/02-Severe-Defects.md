# Severe Defects

Four defects are serious enough to describe in full. The owner of each fix comes from the role table in the README.

D-01 (critical) is the hardcoded fallback session secret in config/session.js, owned by XU Lanxin. The middleware signs cookies with SESSION_SECRET or a fallback string that is written in the source. To reproduce: start the server with SESSION_SECRET unset, base64url-encode a fake user object such as `{"user":{"username":"s9999999","name":"Forged User"}}`, sign the string `comp3810_session=<payload>` with keygrip using that fallback key, then send `comp3810_session` and `comp3810_session.sig` as cookies to /auth/me. The expected result is 401; the actual result was 200 with the forged user, and the dashboard showed "Forged User". This bypasses login completely. The fix is to remove the fallback, require a random secret of at least 32 characters at startup, and fail to start when it is missing.

D-02 (high) is plain-text passwords in models/schema.js, routes/auth.js and seeddata.js, owned by Chi Xuanyi and Cao Fei. Reproduce by running `npm run seed` or signing up, then reading the users collection: the password field holds the literal string, and login compares it with `===`. Expected is a salted hash with a constant-time compare; actual is that anyone with a database read gets every password. Add a bcrypt pre-save hook on the User schema, use bcrypt.compare in login, and migrate the seeded records.

D-03 (high) is the search box passing a raw regex to MongoDB in routes/index.js, owned by XU Lanxin. Reproduce by logging in and opening `/books/search?type=title&q=%28`. Expected is 400 or no results; actual is a 500 with "Regular expression is invalid: missing closing parenthesis". The `q` value goes straight into `$regex`, so a crafted pattern can also slow the server down. Escape regex characters, cap the length, return 400 for bad patterns, or use a text index.

D-04 (high) is invalid book IDs returning 500 in routes/index.js, also owned by XU Lanxin. Reproduce by logging in and opening `/books/notanid/edit` or posting to `/books/notanid/delete`. Expected is 404, as PUT /api/items/badid already returns; actual is 500 with "Cast to ObjectId failed" in the body. Four handlers share the problem. Check `mongoose.Types.ObjectId.isValid` before the query, add one `router.param('id')` guard, and map CastError to 404 in the error handler.
